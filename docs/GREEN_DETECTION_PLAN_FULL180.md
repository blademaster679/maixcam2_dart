# 全视野 180 fps 绿灯识别更新方案

更新日期：2026-09-09  
审查基线：`66abc95788c8e5b96d0355762b0436495e2d300e`

本文取代 README 中 2026-09-02 的 60 fps 历史执行计划，作为后续绿灯、装甲板和
模型开发的当前路线。现有 480×360@60 配置继续作为可回退基线，不删除、不改参数。

## 结论

OS04A10 的全视野 1344×760@180 fps 足以作为比赛主模式，而且比 640×360@360 fps
裁剪模式更适合 15～25 m 初始捕获。180 fps 模式已经证明传感器、VIN、NV21 和应用取帧
可以连续运行 30 分钟；当前瓶颈不是传感器帧率，而是全视野候选质量、候选确认方式、
真实标定与带真值验收。

360 fps 裁剪模式只在以下条件全部满足后作为末端实验项：目标已经稳定锁定、预测位置
确定落入裁剪视野、切换和恢复不会制造控制空窗、裁剪模式另有内参与曝光标定。当前不做
运行中 180/360 动态切换，也不让 360 fps 研发阻塞全视野识别。

审查时工作区无未提交改动，`main` 与 `origin/main` 都位于上述基线。自原 v0.2 主提交
`0f3018e` 起，仓库增加了高速驱动/验证工具、最新帧所有权槽、NV21 搜索、原图 ROI、
异步日志、视觉/装甲分频调度及实测证据。主机验证结果为：

- C++：`green_detector_tests`、`async_frame_tests`、`async_log_tests` 全部通过；
- Python：高速工具 14 项单元测试全部通过；
- `git diff --check` 通过；
- 30 分钟全视野业务测试取得 324245 帧，平均 180.135791 fps，测量窗口无序号缺失、
  重复、逆序或 PTS 倒退，DMA lease 全部归还；
- 已验证的 90/60 Hz 绿灯/装甲基线，控制估计约 180 Hz，接收后的源年龄 P95 为

尚未标定，PTS 对应曝光的阶段未知，真实 Pose 模型也尚未接入高速管线。

## 必须先解决的设计问题

### P0：搜索候选被串行送入单一确认器

`nv21_green_proposals()` 返回最多 5 个点，搜索状态每个绿灯检测周期只轮换处理一个
96×96 ROI，而 `TemporalTracker` 只保存一个待确认目标。默认 90 Hz 下，同一候选在
5 个候选时约每 55.6 ms 才被再次访问；三次命中从第一次到第三次至少约 111 ms，尚未
计入最长 33.3 ms 的全视野搜索等待。不同位置的候选还会重置同一个 tentative track。
因此当前结构不能证明 100 ms 捕获率，复杂背景中甚至可能一直无法确认正确候选。

解决办法是先在全视野层维护最多 5 条彼此独立的轻量候选轨迹，再只把已经积累时序证据
的候选提升给主 `TemporalTracker`。主跟踪器不能直接接收轮询中的不同物体。

### P0：NV21 全视野候选过于简化

当前前端使用固定 `U/V < 128`、固定绿色响应阈值、每 64×64 tile 一个极大值、48 px
合并，最终只输出无尺度、无分数的坐标。它还没有实现原方案要求的局部背景归一化、
多尺度响应、饱和白芯/绿色外环和亚像素中心。这在 LED 屏、反光和小目标低色度场景下
既可能漏检，也可能让硬负样本占满前五候选。

### P0：没有全视野模式的标定与真值

当前 `fx=fy=1344` 只是归一化占位，捕获锥关闭。现有“直接观测 Hz”没有人工真值，
不能解释成召回率；以前九段 OS04D10/低分辨率录像可做旧算法回归，但不能代表
OS04A10 1344×760@180 的像素尺度、ISP 色彩和运动模糊。

### P1：运动补偿缺少变换时间区间

`MotionPrior` 只有结果时间戳，没有 `from_timestamp_us`；异步线程得到的是相邻运动帧
之间的变换，却可能在更晚的绿灯帧上应用。后续需要记录变换起止时间，按目标跟踪器的
测量时刻组合或丢弃变换，禁止仅因“结果不超过 50 ms”就把延迟变换当成当前变换。

### P1：高速入口仍是隔离验证程序

普通 MaixCDK APP 在 `camera.fps > 60` 时明确拒绝运行。高速业务入口尚未纳入正式安装包，
并且构造函数禁止 NPU/Pose。这个边界在算法和数据验收前应保留；完成经典链路后，再把
官方 VIN 初始化与高速管线整理成正式可部署入口。

### P1：曝光到控制的真实延迟未知

现有 P95 是“主机收到 VIN 帧以后”的软件年龄，不含曝光相位和跨时钟偏移。需要同步闪灯
或有时间真值的运动实验确定 PTS 语义，接通 UART/CAN 后还要测完整输出延迟。

## 更新后的无模型主链路

### 1. 采集、搜索和输出分开计数

| 阶段 | SEARCH / REACQUIRE | TRACKING / COASTING | 说明 |
| --- | ---: | ---: | --- |
| 传感器与应用取帧 | 180 Hz | 180 Hz | 每帧记录序号、PTS 和主机接收时刻 |
| 全视野 NV21 搜索 | 先以 60 Hz 验证 | 30 Hz 安全刷新 | 当前 30 Hz 搜索 P95 约 3.6～4.3 ms，有提频空间但仍需实物复测 |
| 绿灯局部精定位 | 每帧最多 1 个 ROI，目标 180 Hz 总预算 | 目标 180 Hz | 搜索时在候选轨迹间调度，锁定后始终优先主轨迹 |
| 装甲几何 | 不运行或低频 | 先保持 60 Hz | 仅在绿灯尺度达到阈值后运行；最大 ROI 验收后再尝试 90/120 Hz |
| 全局运动补偿 | 可关闭 | 先 30 Hz，对比 60 Hz | 只有准确率实验证明有收益才提频 |
| TargetEstimate | 180 Hz | 180 Hz | 预测输出不等于直接观测；两项指标分开记录 |
| NPU 验证 | 暂不运行 | 暂不运行 | 下一阶段使用独立 latest-wins 队列，目标 30 Hz |

### 2. 全视野候选结构

把 `std::vector<Point2f>` 替换为带证据的 `GreenProposal`：

- 源图坐标、估计直径、包围框和亚像素中心；
- `2G-R-B` 或等价 YUV 绿色响应、绿色占比、亮度；
- 局部内核与外环的均值/方差、对比 z-score；
- 饱和白芯和绿色外环分数；
- 综合分数、所在尺度、源帧序号和时间戳；
- 是否位于已标定的 ±6.5° 控制捕获锥。

使用 2/4/6/9/14/20 px 多尺度 DoG 或圆形内核/外环积分响应。全视野阶段只负责高召回，
保持最多 5 个经过非极大值抑制的候选；完整 RGB 算法仍只在局部 ROI 中运行。

### 3. 候选轨迹库与 100 ms 捕获

新增最多 5 条 `ProposalTrack`，按位置、尺度、外观和时间做独立关联。每次 60 Hz 全视野
扫描同时更新所有候选轨迹，推荐初值为 3-of-5 确认；在连续扫描下，从第一次看到目标到
三次证据只需约 33.3 ms。局部精定位按“已命中次数、综合分数、距上次验证时间”排序，
在后续 180 Hz 帧中逐个验证，不再用一个全局 cursor 轮换并重置主跟踪器。

候选只有同时满足以下条件才提升为主轨迹：

1. 位于控制捕获锥；
2. 全视野候选轨迹已满足时序确认；
3. 至少一次局部 RGB 精定位通过，且位置/尺度与 proposal 一致；
4. 若灯条已经可见，则预期颜色和装甲几何一致；
5. 后续启用模型后，再增加模型关键点一致性门。

LED 屏和锥外绿色候选仍保留在调试日志中，但不得产生 `safe_for_control=true`。

### 4. 锁定、丢失与重捕获

- 锁定后每个可用视觉周期优先处理预测 ROI；ROI 按实测目标几何确定，不只使用固定
  `12×绿灯直径`，并验证 128～384 px 上限能覆盖全滚转装甲；
- 任一直接漏检立刻并行恢复 60 Hz 全视野搜索，不能等待窄门限耗尽；
- 纯预测最多 2 个输出帧或 35 ms，超过后继续报告预测但控制无效；
- 新候选不得立即替换正在 COASTING 的主轨迹，必须经过独立候选确认和换轨门；
- 日志分别记录 proposal 命中、ROI 验证、主轨迹直接观测、预测、错误换轨和控制状态。

### 5. 装甲、位姿与模型

远距离仍以绿灯视线为主。接近后从红/蓝双灯条提取五关键点，使用实物测量模板做
IPPE/PnP；完整端点、足够分离度和重投影误差不超过 2 px 时才输出有效位姿。

模型继续采用局部 YOLO11n-Pose，而不是整幅 1344×760 推理。高速管线增加独立 NPU
线程和容量为 1 的 latest-wins 队列；每个请求/结果必须携带 `source_sequence`、源时间戳、
ROI 和候选轨迹 ID。过期、换轨或空间不一致的结果只记录，不能解除安全门。先测
192/256/320，默认 256；设备 P95 超过 20 ms 才考虑 192，准确率不达标则不能通过。

## 后续具体步骤

以下顺序避免重复已经完成的驱动和 180 fps 连续性工作。

### 第 1 步：固化本次基线并采集原生数据

1. 保留当前 `66abc95` 为全视野业务基线，新建功能分支开发候选轨迹库。
2. 固定比赛镜头、焦距、光圈和安装方向；不要在后续数据之间重新对焦。
3. 用原生 1344×760@180 录制 5/10/15/20/25 m、红蓝两色、±5°、全滚转、横移、
   失焦、曝光变化、遮挡和无目标场景。每段同时记录曝光、增益、WB、距离和场景编号。
4. 先完成至少 30 分钟无目标/LED 屏/反光背景硬负样本；现有 0/1 号 LED 屏继续保留，
   但只作为跨相机回归材料。

录制前先复现当前高速构建和 10 秒短测：

```bash
python3 tools/os04a10_highfps/build_official.py \
  --out .maixpy/business-full180-next --business

python3 tools/os04a10_highfps/run_device.py \
  --driver-build .maixpy/business-full180-next \
  --official-mode full180 --seconds 10 --nv21 \
  --itp-depth 4 --queue-depth 4 --system-media-lib \
  --remote-root /root/os04a10-tests --pause-camera-app \
  --business-config config/green_detector_full180.conf
```

完成条件：视频/采样帧和 `source_sequence`/PTS 能对应；每段元数据齐全；原模式退出恢复
通过。单独录制 H.264 只能验证可见内容，不能替代业务 NV21 序号和时间证据。

电脑不能留在现场时，使用已经实现的
[离线录制 APP](../tools/offline_recorder/README.md)。每次从桌面启动后需在确认页按下并松开
`START RECORDING`，随后才分配持久 clip 编号、录制并执行完整性检查；重连电脑后用
`pull_recordings.py` 校验并拉取。板端时钟
可能不准确，因此现场记录以 clip 编号为准。

### 第 2 步：完成 1344×760@180 标定和曝光扫描

1. 在相同 VIN/ISP 路径采集不少于 20 组覆盖全画面的标定板图像；求内参、畸变和
   重投影误差，保存镜头、分辨率、模式和日期。
2. 测试 100/200/400/500/800/1600 μs 及必要增益，固定 WB；用有速度真值的运动目标
   采集时可直接在离线录制APP的横屏面板调整 `TIME/EXPOSURE/GAIN`，每次开始后选择会
   写入 `record_context.json` 并供下一段沿用，减少现场重复编辑配置文件。
   测拖影，而不是仅凭静态画面选择曝光。
3. 写入新的比赛配置后开启捕获锥，锥外目标只作调试。更换镜头、焦距、分辨率或模式
   必须重新标定。

完成条件：标定 P95 重投影误差有记录；25 m 绿灯仍有可分离响应；最大工况拖影不超过
1.5 px；角度输出才允许从无效改为有效。

### 第 3 步：重写 NV21 proposal 与候选轨迹库

主要修改：

- `main/include/dart/nv21_pipeline.hpp`：增加 `GreenProposal`、`ProposalTrack`、统计接口；
- `main/src/nv21_pipeline.cpp`：多尺度局部归一化、候选关联、状态相关搜索频率和调度；
- `main/include/dart/green_detector.hpp`、`main/src/config.cpp`：增加可配置阈值及
  SEARCH/TRACKING 两套频率；
- `tests/test_green_detector.cpp`：加入五候选轮换、100 ms 确认、交叉换轨、LED 硬负、
  边缘 ROI 和 2～20 px 尺度测试。

先只输出 shadow 指标，仍保持 `safe_for_control=false`。完成条件：锁定测试集 proposal
top-5 召回不低于 99.8%，100 ms 捕获成功率不低于 99%，无目标区间控制级输出为 0；
最大 ROI 场景下应用取帧仍接近 180 Hz且无上游缺号。

### 第 4 步：建立可重复的无模型验收

1. 给原生全视野数据标注可见区间、绿灯中心、直径、遮挡和源帧序号；装甲可见帧再标
   四个灯条端点与颜色。
2. 扩展回放工具，使它能复现 NV21 proposal、候选轨迹库和状态相关调度；普通 RGB
   `video_replay` 的结果不能单独代表直接 VIN 路径。
3. 每次参数修改自动输出按距离/场景拆分的捕获延迟、top-K 候选召回、直接观测率、
   最长预测区间、错误换轨和无目标误报，不再以“输出了多少框”代替准确率。
4. 比较 90/60、120/90 和 180/60 三种绿灯/装甲预算；选择满足准确率和 P95 延迟的最低
   负载档，而不是直接选择调用频率最高的配置。

完成条件：无模型锁定测试固定，阈值不再用测试集调整；至少完成三次 30 分钟最大 ROI
板测，并记录 Sensor、VIN、NV21、应用取得、直接检测和 TargetEstimate 六种频率。

### 第 5 步：修正运动补偿时序

给视觉变换增加起止源时间，按区间组合到当前跟踪状态；结果晚到、区间重叠或缺口过大时
丢弃。用已知平移、滚转和快速扫动序列比较 30/60 Hz，只有关键点/视线误差显著下降且
延迟仍通过时才选择 60 Hz。

完成条件：运动补偿不会重复应用或应用到错误帧；开启补偿后的错误换轨和 P95 角度误差
均不劣于关闭补偿。

### 第 6 步：完成装甲几何和 Pose

测量本赛季灯条长度、中心距以及绿灯到装甲中心的二维/三维偏移，验证红蓝、全滚转和
距离退化。根据几何比例重新确定 ROI 大小；如果 384 px 不能覆盖近距离装甲，先评估
分块或定向 ROI，不能静默裁掉灯条端点。

完成条件：完整灯条时关键点 P95 不超过 2 px、PnP 重投影不超过 2 px、滚转误差不超过
3°；灯条过小时只输出绿灯视线，不强行输出距离或位姿。

### 第 7 步：训练并异步接入模型

按完整录像和场地划分至少 1 万正 ROI、2 万硬负 ROI，第三场地锁定测试。训练
YOLO11n-Pose，生成固定输入 INT8 AXMODEL/MUD，再实现高速管线的独立 NPU worker。
模型只验证候选和关键点，不替代 180 Hz 传统跟踪。

完成条件：锁定测试集正候选召回不低于 99.5%，关键点回原图 P95 不超过 2 px，控制级
误报为 0；板端模型 P95 不超过 20 ms，端到端 P95 不超过 30 ms。

### 第 8 步：正式入口、控制链路和最终验收

将已经通过前述验收的 VIN 高速入口纳入正式 APP 构建，统一资源退出和故障恢复；再为
同一个 `TargetEstimate` 接 UART/CAN，加入序号、时间同步、CRC 和超时失效。先台架硬件
在环，最后做至少 300 次 15～25 m 独立测试。

最终条件：100 ms 捕获成功率不低于 99%，融合控制有效帧不低于 99.5%，捕获后控制无效
间隔不超过 50 ms，无目标或错误颜色进入 `safe_for_control` 的次数为 0；持续 180 fps
采集、P95 延迟和温度/RSS 均通过 30 分钟以上测试。

```bash
cmake -S tests -B build/tests -DCMAKE_BUILD_TYPE=Release
cmake --build build/tests -j2
ctest --test-dir build/tests --output-on-failure

cd tools/os04a10_highfps
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest \
  test_tools test_fullfov test_business_analysis
cd ../..

git diff --check
git status --short
```

高速板测仍按“5～10 秒短测 → 30 秒空载 → 2 分钟最大负载 → 30 分钟长测 → 原模式恢复”
执行。任何阶段失败都保存失败证据并先恢复相机服务，不直接进入下一阶段。
