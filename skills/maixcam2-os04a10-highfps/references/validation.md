# 真实帧率与稳定性验收

## 先定义测量点

报告中分别标明 sensor/VIN RAW、ISP/IVPS NV21、应用消费、显示和编码速率；选一种明确的采集输出作为该轮验收对象。RAW 达到 360fps 不代表 NV21 已达到。

记录请求模式、实际输出模式、RAW 位深、曝光/增益、ROI/视野、AI-ISP、缓冲策略、版本和加载库哈希。每帧或无损批量元数据至少包含：

```text
stream/session ID, driver sequence (若可得), hardware PTS (若可得),
PTS 单位与来源, host monotonic timestamp, width, height, format,
acquire/release result, sampled image identifier
```

使用 SDK 文档和实际头文件确认序号来源、计数位宽、回绕、时间戳单位，以及 PTS 对应 SOF/EOF/ISP 哪一时刻。无法获得硬件信息时标记未知，不伪造字段。

## 验证真实更新

- 对有效帧计算 `(N-1)/(t_last-t_first)`；PTS 和 monotonic 两个时基分别统计并交叉核对。报告 P50/P95/P99/最大帧间隔和固定时间窗口帧率。
- 根据已确认的硬件序号语义统计跳号、重复、逆序、回绕与重启；排除预热阶段并报告预热时长。序号若由软件每次 GetFrame 生成，就不能单独证明新的曝光。
- 对受控动态场景抽样核验真实画面更新，可使用已知时间变化的光源/运动图案。结合帧序、PTS 和图像内容判断缓存重发。图像 hash 相同不能单独证明重复曝光，噪声导致 hash 不同也不能单独证明真实帧率。
- 不用显示器标称刷新率或短曝光代替采集测量；rolling shutter 的逐行读出时间也应与整帧更新率区分。

## 阶段门槛

先复现当前 OS04A10 默认模式。仅对时序资料支持的档位做 120→180→240→360fps 递进；每档先做短时点亮，再连续 30 分钟，最终目标额外覆盖冷机启动、热机运行、退出重开和回退。

以下为本项目建议验收门槛，并非厂商性能保证；用户可以在正式测试前调整：

| 指标 | 目标 |
| --- | --- |
| 模式 | 实际有效图像 640×360，输出格式和视野方案与声明一致 |
| 速率 | 最终模式连续至少 30 分钟，平均 ≥359fps；检查每 10 秒窗口，报告低于 359fps 的窗口与原因，不能只交总平均 |
| 连续性 | 无未解释的硬件丢帧、重复帧、逆序或收帧超时；明确消费者主动丢弃与上游丢失的区别 |
| 总线与图像 | MIPI CRC/ECC/overflow 等可用计数在测试中无异常增量；无花屏、错位、Bayer 错配、截帧 |
| 热与内存 | 记录环境温度、可得的 SoC/传感器温度、时钟、CPU/RSS、pool；无持续增长、降频失速或超过厂家额定限制 |
| 恢复 | 实验正常退出和异常退出后均可恢复原模式，重复打开不漏资源 |

缺失 CRC/ECC、硬件序号、温度等关键观测时报告“该项未验证”，并写明补充手段。没有观测到错误与证明没有错误不是同一个结论。短时、平均值或软件计数达标只可标记阶段通过。

## 故障定位与交付

- 无 RAW：检查实际库、chip ID、模式分发、供电/复位/时钟、MIPI 参数和 VIN 配置。
- RAW 速率低：核对实际 HTS/VTS、PLL、曝光/AE 是否拉长帧、模式回退以及接收计数。
- RAW 达标而 NV21 低：检查 ISP/IVPS 节流、处理模式、pool 和带宽。
- NV21 达标而消费低：检查拷贝、日志、缓冲归还、编码、磁盘与网络，不能反向修改传感器来掩盖消费瓶颈。

最终交付包含可复现命令、版本与哈希、补丁、mode manifest、测量程序、原始指标、抽样图像、稳定性结论和验证过的回退步骤。报告明确写“360fps 已验证”“仅某输出层通过”“仅较低档通过”或“资料/硬件约束尚未解决”。
